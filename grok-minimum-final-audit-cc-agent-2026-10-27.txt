二、新发现(按影响排序)
 N1【P1,静态,未复现】生产 CREATE 出来的 Mode A VM,内核数据面一出本机就不工作。
     协调器分配 VM ID 永远用 U32 命名空间(wavevm_coordinator.c:793-794、1051;wavevm_identity.c allocate_fresh_id 对 U32 跳过 <256),所以生产 VM ID 恒 ≥256。
     内核 wvm_wire_encode_id(kernel_backend.c:844-857)对 vm_id>255 直接返回 -EOPNOTSUPP;它在缺页请求(1370)、两处发送(1619、1674)和 diff 提交(1815)全部被调用;RX 仍用 WVM_GET_VMID 的 8 位解码(2410)。
     准入层没有任何地方拒绝"Mode A + vm_id>255",也没有给 Mode A 分配 ≤255 的 ID。结果:Mode A 的 CREATE 能到 RUNNING(控制面),但任何需要经内核发包的操作都会失败。
     Grok 自己的证据印证了这一点:plan 的 worker_failure_isolation 条目写明原测试用 VM 2101/2102 时因 "need V1 envelope" 卡死,后来是把测试改成 VM 91/92 才"FIXED"——即用测试规避了生产 ID 范围,而不是让生产路径支持。
     plan 里 A04 标 "FIXED*"(8 位 wire):这只是让它 fail-closed,不是修好。纲领方向是完整 u32 身份,不能靠缩小 VM ID 范围代替。
     影响:Minimum 第 5 条("Mode A 在多 VM 主机上宣告前必须有两 VM 隔离测试")——隔离测试本身存在,但它们在 ≤255 的 ID 和本地 mmap 上证明隔离;生产 ID 下 Mode A 数据面不可用,"可宣告 Mode A 多 VM"不成立。
 N2【P1】§7 guest 冒烟的"远端 vCPU/内存证据"判据是日志 grep,不是证据。
     tests/e2e/test_guest_smoke.sh:348-385:remote_vcpu=1 只要 agent.log 出现 "TCG PROXY"/"local executor READY..."/"KVM FAST PATH" 这类 executor 启动横幅;remote_mem=1 只要日志匹配 WVM-REMOTE|VCPU_RUN|dirty|COMMIT|region_add|WaveVM 之一——"WaveVM" 这个词几乎任何 wavevm 日志行都带。
     纲领 Phase 10 明说"进程存活或端口监听本身不是成功判据",要求证明远端 vCPU 和远端内存路径被实际执行。这个判据证明不了,所以 §7 的 OVERALL=PASS 不能支撑纲领第 9 条。
     应改为:登录后断言可核对的计数——远端节点上完成的 VCPU_RUN 次数、内存 ack/commit 次数及页版本前进,>0 才算。
 N3【P1】TCG 多 vCPU 的"稳定"依赖按实验调出来的启发式,且很可能让 guest 启动窗口在本地执行。
     wavevm-cpu.c(未提交):默认 stop-the-world 串行化远端切片(注释承认 SHM 并发 TCG 会导致 guest 内存计数损坏/时钟不稳/DHCP 挂死);为避免 FE 与 BSP 互相饿死,加了 force_local、prefer-local、sticky 窗口。
     注释里直接写"Window 60s covers Cirros boot-to-login under remote TCG",预算 5/8/12ms、spin 阈值 2/4/8、60 秒墙钟窗口都是硬编码,来自一连串 attach18→attach40 的实机试验。窗口一旦武装,consume_force_local 对所有 vCPU 返回 true,即启动到登录这段 vCPU 都在本地跑。
     plan 的 A/B(attach40)显示关掉 force_local 后 guest 在 ~182s 冻住,所以它不是可选优化。另外还留了两个环境变量开关(WVM_TCG_SHM_CONCURRENT、WVM_TCG_DISABLE_FORCE_LOCAL)在生产路径里。
     这违反 goal.txt 自己写的"不添加硬编码或测试专用 workaround",也和纲领"不能为过测试永久全局串行"的精神冲突;与 N2 合在一起:登录窗口内是否有远端 vCPU 执行,当前判据分辨不出来。
     注意:我无法确认实际运行时登录窗口有多少是本地执行(证据已清),这条是"按构造推断"。
     Grok 对此自己已标 PARTIAL,我同意,并认为这不是"调参收口"能解决的:需要找出跨进程 TCG 在 FE 阻塞等待 helper ACK 时互相饿死的根因(例如把 ACK 等待改成不占 remote_active 的异步握手),或者由纲领明确规定 V1 远端 TCG 的合同(见四)。
 N4【P2】committer 对"本地目录/AUTO_ROUTE"把 diff 发送短路成成功(committer_thread_fn,kernel_backend.c:1733 起)。
     plan 说明动机是 test_worker_failure_isolation 在单机无对端时 -ENODEV 会让页面 mkwrite 假 SIGBUS——即为让测试通过而改生产路径。
     两个问题:(a) 目录是本地节点时,diff 没有被送到任何地方,本地权威存储是否仍能拿到更新,需要设计说明;(b) AUTO_ROUTE 表示"路由未绑定/未知",不是"本地",把它当成功等于静默丢写而不是 fail-closed(上一轮 F4 已经讲过同一原则)。
 N5【P2,静态】A02 修复把 per-CPU 槽位的持有区间扩到了一次可能睡眠的发送上。
     committer:wvm_set_active_context → wvm_get_directory_node_id → k_send_packet_ctx → wvm_clear_active_context。发送在非原子上下文走 raw_kernel_send(我读的是旧版 k_send_packet 的结构,没有重读 k_send_packet_ctx),可睡眠;睡眠中迁核会让 clear 清掉别的 CPU 的槽,原 CPU 的槽保留指向可能随后释放的 context 的悬空指针。
     而 explicit-context 版本的发送本身不需要这个槽,只有目录查询需要。建议只在目录查询前后 set/clear,或给目录查询也传显式 context。这也是 A01 的根因没有被消除。

六、纲领层面的问题(单独列,给用户/Codex agent 判断,不是 Grok 的错)
  远端 TCG 多 vCPU 的合同在纲领里没有写清:Grok 的实机结论是"跨两个 QEMU 进程共享 SHM 的并发 TCG 不安全,必须串行(STW)",这是一个会影响 Minimum 范围的设计事实。
  需要在 vcpu-handoff / capability-fault-engines 里明确 V1 的选择:(a) V1 远端 TCG 就是串行切片,并写出界限和饿死处理的正式机制;或 (b) 要求真并发,并写出内存模型要求。当前由实现者通过调参来决定,这不合适。
  同理,Mode A 与 VM ID 范围的关系(legacy 8 位 wire 与 U32 身份并存)需要纲领明确:要么 Mode A 数据面必须支持 U32(V1 envelope),要么准入对 Mode A 约束 ID 范围并写进合同。
