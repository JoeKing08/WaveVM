WaveVM Minimum 独立初审：Codex agent
日期：2026-10-27
用途：交给 CC agent / DSH agent 交换交叉审计意见；不是汇总后的最终裁决。

一、结论

当前不能签署“纲领 Minimum 已逐条完成，代码质量过关”。

控制面、manifest、成员事务、放置和 runtime 的主体已经存在，并非仍停留在
早期骨架状态。本轮 19 个现有针对性测试中 17 个通过，但发现以下 9 项问题。
其中有生产路径正确性缺陷，也有会把本地启动误记为分布式验收通过的判据。
不能把它们统一归为“只影响性能”或“以后 Extended 再补”。

本结论不否认某些 Cirros 运行已经登录/SSH 成功；它否认的是由此推出
“所有 Minimum 合同均成立”。本轮没有重新跑完整 guest，不对旧启动日志
作真伪断言。

三、发现（P1：应在签 Minimum 前解决；P2：构建/交付缺陷）

R1 [P1] 本机 SHM 被错误扩展为全 VM 分布式内存一致性豁免

位置：
  wavevm-qemu/accel/wavevm/wavevm-all.c:1982、2141
  wavevm-qemu/accel/wavevm/wavevm-user-mem.c:1730、2296
  wavevm-qemu/accel/wavevm/wavevm-cpu.c:1998
  common_include/wavevm_identity.c:455

TCG frontend 只要成功接上本实例的 WVM_SHM_FILE，默认就置
g_tcg_shm_coherent=1；helper 也因自己接上本节点的文件而置位。
然后 frontend handoff dirty flush、helper dirty flush 和相关 fence 被跳过。
这没有核对目标 executor 是否与 frontend 共享同一 RAM backing，也没有核对
该页的 directory / subscriber 是否只位于这个共享映射中。

一个节点上的共享映射，只证明该节点相关进程可以看到同一物理页。
另一 compute 实例的 SHM 名包含自己的 physical_node_id；即使同机部署，
它也不是自动与 frontend 共享同一个文件。更不能据此省掉跨节点的版本提交。
触发多节点 TCG handoff 时，目录和其他节点可以继续看到旧数据，helper 的
写入也可以不经过权威 commit。

依据：memory-consistency §4.2/§4.6、baseline §4.3/§9。
最小修法：把本地 alias 优化限制到已证明共享 backing 的具体边界；远端
directory/subscriber/handoff 继续走生产 commit/ACK/fence。不要把关闭环境
变量作为最终验收时的必要 workaround。
最小验证：两个不同 node runtime/SHM 的 TCG 参与者，guest 写入之后在远端
权威目录检查数据和版本，并反向读取；测试端不得代提交。

R2 [P1] 启动成功依赖针对 Cirros 启动时长设置的全 vCPU 本地退化

位置：
  wavevm-qemu/accel/wavevm/wavevm-cpu.c:392、639、661、2495
  docs/wavevm-architecture-baseline.md:1004

相同 RIP 多次返回后设置 force_local；并设置 60 秒 sticky 窗口。
窗口内 consume_force_local() 对所有 vCPU 都可返回 true，即使其预算已耗尽。
主循环据此绕过 schedule_policy() 选出的 remote executor，直接本地执行。
代码注释明确把 60 秒解释成覆盖 Cirros boot-to-login。

这不只是时间片的性能调节：它把 manifest 放在其他节点的 CPU 工作搬回
frontend，既不能证明资源池生效，也可能突破 host_node 的 CPU 记账。
本地 MTTCG 与远端切片之间的全局 STW 还意味着独立 vCPU 的并行合同未证明。
RIP 重复本身不能证明远端资源故障或授权本地替代执行。

依据：baseline §2/§15、vcpu-handoff §8、resource-placement-admission §7。
最小修法：解决持锁/等待与本地设备或 vCPU 进展之间的调度依赖；如确需
局部 fallback，必须有与 guest 镜像无关的触发、受限作用域、资源许可和
可观察的恢复，不能靠覆盖启动时长获得 PASS。
最小验证：SSH 后执行受控 guest 工作负载，目标远端的成功执行计数持续
增长，frontend 没有把所有远端 vCPU 长期接回；不能只取启动早期累计值。

R3 [P1] push fence 用睡眠代替完成 ACK，且下层失败仍回复成功

位置：
  slave_daemon/slave_hybrid.c:4592、4635、4648
  master_core/main_wrapper.c:1475
  wavevm-qemu/accel/wavevm/wavevm-user-mem.c:2587、2648

wavevm_proxy_barrier_local_helpers() 发送 UDP barrier 后只睡 2000us，
未收齐/核对 cookie ACK，且只要至少一个 helper sendto 成功就返回成功。
main_wrapper 对本地 QEMU barrier 的 br 只打印，对 helper barrier 的返回值
直接忽略，随后无条件写 16 字节全零回包。
QEMU 的 explicit-fd fence 读够这 16 字节便返回成功。

因此 helper 尚未 APPLY、某个 helper 没收到、或 barrier timeout 时，
后续 CPU_RUN 仍可被当成已同步继续执行。UDP 发送成功和睡够 2ms 都不能
证明 receiver 已安装页面。现有 push listener 已有 PUSH_BARRIER_ACK，
问题是生产调用链没有完成关联和错误传播。

依据：memory-consistency §4.6；vcpu-handoff §5。
最小修法：复用现有 barrier/cookie，等待所需参与者真实完成 ACK；失败沿
IPC 状态传回并禁止本次 handoff。无需新建一套故障引擎。
最小验证：暂缓一个 helper 的 APPLY/ACK，fence 不得提前成功；恢复后完成，
超时则返回显式失败，不能回全零成功包。

R4 [P1] 为解决记录表满而提前删除 vCPU 完成记录，已复现回归

位置：
  node_runtime/vcpu_coordinator.c:883
  tests/control-plane/test_vcpu_coordinator.c:554

complete() 回调返回后立即 entry_clear(done)，无论结果保留 horizon 是否
结束，也无论回调本身是否成功。生产回调只把 ACK 排队并不证明调用方已收到。
随后相同 VCPU_EXIT 找不到原操作，lookup_completed 也失去结果；同一
operation_id 再 submit 可以进入新操作分配路径，不再保留原 handoff sequence。

独立运行：bash tests/control-plane/test_vcpu_coordinator.sh
退出码 1：vCPU coordinator test: accept an exact duplicate exit idempotently。
这是现有合同测试失败，不是新增一个罕见场景来提高验收要求。

依据：vcpu-handoff §6（容量不足必须 backpressure，不能提前淘汰）、
identity-routing §6.1。
最小修法：保留约定 horizon 内的结果/身份，正确预算容量与回收；局部 IPC
waiter 可释放，不等于可以清掉语义完成记录。
最小验证：现有 coordinator 测试通过，并保持同一 operation_id 重发/查询
的 sequence、结果不变；表满时在执行前显式背压。

R5 [P1] ESTALE 重试只刷新版本，却把旧整页数据盖到新版本上

位置：
  wavevm-qemu/accel/wavevm/wavevm-user-mem.c:1818、2225

commit 遇到 ESTALE 后读取 mat_page，但忽略权威页面字节；只采用
mat_ack.version，随后重发旧 HVA/current_snapshot 的整页内容。
slave 分支注释甚至明确说明“keep slave snapshot bytes”。

例：A、B 从同版 [x=0,y=0] 开始；B 写 y=1 并提交；A 的旧快照是 [1,0]。
A 收到 ESTALE，取到 B 的新版本号后直接提交旧 [1,0]，合法的版本号无法
阻止 B 的 y=1 被覆盖。一次重试也会丢数据，问题不在重试次数。

依据：memory-consistency §4.2/§4.3：客户端整页快照不能作为覆盖更新目录
的通用恢复捷径。RESYNC 必须处理数据，不是给旧数据换个 base 标签。
最小修法：保留真实写集并在权威页上正确重放，或显式失败/重新执行受控
操作；无法证明写集时不要提交旧整页。
最小验证：两个节点修改同一页的不同字节，在 stale/resync 后两个修改都在；
改同一字节按约定拒绝/排序，不能静默吞掉另一已确认提交。

R6 [P1] Mode A 隔离修复仍绕过生产脏页语义，并保留 8-bit 数据面

位置：
  master_core/kernel_backend.c:844、1619、1815、1868
  master_core/logic_core.c:1383
  tests/mode-a/test_worker_failure_isolation.c:31

有两个独立问题需要分别修正：

1. 新 committer 将 !WVM_IS_VALID_TARGET(dir_node) 也当成本地成功。
   directory lookup 在无 context、未绑定 route snapshot 或 GPA 不在
   admitted memory projection 中时恰好返回 WVM_NODE_AUTO_ROUTE。
   这些失败不是本地 owner 证明；当前却会跳过提交，进入 reprotect/free
   正常结束。即便真实目录在本地，也需完成目录版本/订阅者更新，不能
   只凭“无需网络发送”就把 commit 视为成功。

2. BIND 的 identity 是 u32，但 fault/committer 仍调用只接受 vm_id<=255
   的 wvm_wire_encode_id。高 ID fault 把 slave_id 置零后继续发送；
   dirty 分支则释放唯一任务后 continue，没有把失败上报为同步失败。
   本次 worker_failure 测试把 VM 2101/2102 降为 91/92，避开了原问题。
   这不能满足 kernel-accelerator §1.2 的 full-u32 数据路径要求。

依据：kernel-accelerator §1.2/§5.1、memory-consistency §4.2、
baseline §5/§13（内核只加速，不建立另一套成功语义）。
最小修法：缺路由时 fail closed 并保留脏页；本地 commit 进入同一权威语义；
完整身份经 canonical node-runtime 数据路径处理，不能靠低 ID 测试规避。
最小验证：保留高于 255 的 Mode A VM 做真实 mmap fault/write；断开所需
route snapshot 时必须失败而非 commit success；双 context 隔离继续成立。
本轮没有 /dev/wavevm，以上为源代码确认，未声称动态重现内核故障。

R7 [P1] STOP drain 不包含正在写 ACK 的线程，可返回成功后无限等待

位置：
  node_runtime/vcpu_service.c:169、346、442
  node_runtime/vcpu_service.c:139
  node_runtime/main.c:1378

reply_worker 在 write_reply 前已清空 entry 并通知 drain。
drain 只统计 PENDING/REPLY_QUEUED，没有“发送中”状态；发送遇到 EAGAIN
又进入 poll(POLLOUT, -1)，destroy 中 pthread_join 没有退出边界。
所以新增 coordinator completions_in_progress 确实补到了回调生命周期，
但没有补到最后一跳 ACK writer 的生命周期。

本轮临时复现复用现有 test_vcpu_service 的 admitted fixture：
预先填满 socket 发送缓冲区，接收端不读取，再完成一个真实 coordinator
结果。30ms 后调用 service_drain(timeout=20ms)，输出：
  slow_reader_drain_rc=0 error=
此时 ACK 仍无法写出。复现进程随后直接退出，没有挂住宿主机。

依据：runtime-manifest-lifecycle §6.1：停止需结算/报告所有在途操作，
而不是看不到队列项就宣告完成。
最小修法：跟踪 ACK 正在发送的状态；发送/停止有界且错误可见，join 前
确保发送 worker 能退出。不要只再加一次同样的 drain() 调用。
最小验证：慢/断开的本地 receiver 不能让 drain 假成功或 STOP 无限等待；
正常 ACK 完成和 STOP 仍通过。

R8 [P1] guest E2E 的“远端证据”实际上可以只由初始化日志满足

位置：
  tests/e2e/test_guest_smoke.sh:110、344、359、367、385、392
  tests/control-plane/test_create_vm_single_node.sh:123、227

脚本只注册并使用一个 compute node 801/instance 802，再手工拉起 frontend。
该层可以用于 guest 启动验证，本身不能作为资源来自多个 compute 节点的证明。

remote_vcpu=1 可仅由 “local executor READY with live TCG helpers” 触发；
remote_mem=1 可仅由 WaveVM / region_add 日志触发；另一分支看见 region_add
就直接把两个标志都置 1。helper 已启动和 RAMBlock 已注册，均不代表
已完成目标远端 CPU slice、远端 page read 或 directory commit。
这与 R1/R2 叠加，可以在大部分工作本地运行时得到分布式 PASS。

此外，guest_cpu_smoke 失败被 || true 吞掉；OVERALL=PASS 写在 STOP 之前。
STOP 失败虽会使 shell 返回非零，result.txt 仍保留 OVERALL=PASS。
先杀 FE 再 STOP 的场景也不能覆盖 R7 的在途 ACK drain。

依据：roadmap §14、runtime-manifest-lifecycle 最后一个 Minimum 验收点。
最小修法：记录 VM/incarnation、实际源/目的 compute、已完成 slice ID、
权威页数据/版本的运行期增量；初始化日志只作诊断。最终总结果在 STOP/
cleanup 判定之后输出。多节点 guest 或可组合的分层证据均可，但必须
证明组合使用同一条生产路径，不能把仅组件路径的 PASS 当成当前 guest
路径已同步的证明。
最小验证：禁用实际远端 dispatch/page 请求而保留初始化日志时，本验收
必须失败；真实路径运行时再提供正例。无需新增庞大的测试平台。

R9 [P2] memory_service 现有严格测试无法编译，连带 A14 入口被阻断

位置：node_runtime/memory_service.c:1477、1494

立即 release waiter 后留下两个未使用的 static finish 函数；现有
-Wall -Wextra -Werror 测试报 unused-function。
  bash tests/control-plane/test_memory_service.sh -> rc=1（编译阶段）
test_goal4_executor_remote_memory.sh 的第一步就是执行该测试，因此当前

最小修法：清理真正不用的代码或恢复必要调用，保持既有严格构建；不要
通过删除 Werror 来宣告交付通过。

四、按纲领 Minimum 范围逐项核对

以下是本轮核对范围和可确认的边界，不是把一部分测试 PASS 推广为全系统 PASS。

1. 控制面/manifest/准入事务：
   ctl_tool/main.c 已真实初始化 authority_owner、绑定 admission_authority，
   capture membership 后驱动 admission。控制面成员、authority owner、
   canonical record 测试通过。该项不再是“还没挂到入口”的旧状态。

2. 成员入群、ACTIVE、cordon、drain、gateway replacement：
   生产 enrollment/drain transport 已接入；cluster admission proof、
   membership route、gateway route control 集成测试通过。本轮没有重跑
   所有真实进程 drain/换血用例，不把 plan 里的旧 PASS 重新认作本轮证据。

3. 资源粒度/放置/同机多实例/并发预留：
   placement plan、SPREAD、physical_host aggregate 测试通过；manifest
   派生本地命名已按物理节点区分。R2 的执行时绕过放置不能因 planner
   组件测试通过而被豁免。四并发真实 CREATE 本轮未重跑。

4. Mode B 多 VM 隔离：
   multivm isolation 测试通过；双活 guest 与杀一保一的最新集成证据本轮
   不可见。未发现需要推翻 namespace 设计的新问题，但不能据组件 PASS
   直接盖章活运行隔离全部完成。

5. 生命周期/STOP/部分启动补偿/冷重启对账：
   ctl_tool/main.c:1984 已有真实 recover_midflight_admissions 接线，不能
   说该部分仍完全未实现。正常停止仍被 R7 阻断；本轮未重跑完整恢复集成。
   HA/透明恢复和所有崩溃点矩阵不列为本轮前置要求。

6. 身份/flat/fractal/route generation/容量：
   canonical、cluster snapshot、membership route、gateway route control
   测试通过。flat_gt_4096_fixture 实际 compiled+resolved 4100 条并通过。
   本轮没有独立完成 multi-Pod >4096 的整条 capture/admission/forwarding
   验收，也没有重新执行完整 fractal guest；应与另外两份审计交换证据。

7. wire/local IPC/操作去重：
   codec/规范对象和 executor cache 有实现且相关组件测试通过；R3、R4、
   R6 说明生产调用链仍有绕过合同的缺口，不能用 codec PASS 抵消。

8. 内存一致性/TCG no-root fallback/KVM dirty-resync：
   directory store、fault engine 组件测试通过，生产 memory_service 测试
   未编译通过。R1/R3/R5/R6 均属这里的实际正确性缺陷。
   A14 已把“测试手工提交 guest 写入”改成等待 TCG 自提交，这是正确方向；
   但当前构建和新 SHM 默认分支仍需对齐，不能沿用旧 PASS 代替。

9. vCPU handoff/设备退出/并行与重放：
   vcpu service、executor handoff cache 测试通过；coordinator 重复结果
   测试失败。R2/R4 分别影响真实执行放置/并行与重放语义。

10. Mode A 多 context：
    内核已有真实 registry、per-context 状态和引用回收，不是只有 per-VM
    lease 的假隔离；不过 R6 表明内核数据面合同没有因此自动闭合。
    当前无 /dev/wavevm，未复跑双 context/worker failure 内核用例。

11. 存储与设备权威：
    block service 测试通过，QEMU frontend 设备权威与 typed block 服务
    主体存在。本轮未独立重跑 guest 远端存储与持久化 flush/FUA 链，
    不将 Cirros 的本地 qcow2 启动等同于远端 block 验收。

12. Minimum 矩阵/guest readiness/证据/清理/日志有界：
    s6 分层矩阵和 guest 脚本均存在；当前主要阻断见 R7/R8/R9。
    guest 已有日志 cap/watch 的实际实现，但目录中的工具未全部跟踪，
    发布前需把被脚本引用的新脚本一并提交。未要求重做 Extended CI。
