一、结论

有实质进展，分层方向正确，不需要推倒重写。但本轮存在两个已复现的确定性
错误，尚不能按合格交付收口；队列顺序语义也没有实现。

正面进展：
  - 请求使用显式大端编解码，不再直接把宿主 packed struct 当网络格式。
  - service 使用 envelope 中的来源身份、128 位 operation_id，并校验本地
    VM/incarnation/generation；有 IN_FLIGHT 占位、摘要冲突和结果重放分支。
  - 测试直接驱动真实 wvm_block_service_dispatch 与真实 chunk store，
    比测试内重写一个等效 handler 更有价值。
  - 如实声明尚未安装到 main.c，也没有把 QEMU 发起端和 ACK 返回链宣称完成。

二、需要修复的问题

1. [P1] 40 字节请求头的编码实际写到第 42 字节

位置：
  common_include/wavevm_block_wire.h:61
  common_include/wavevm_block_wire.c:144

WVM_BLOCK_REQUEST_HEADER_BYTES 定义为 40，但编码执行：
  put_be32(bytes + 38, 0);
写入覆盖偏移 38、39、40、41。对于没有数据体的 READ/FLUSH，调用方按头长
分配 40 字节即发生两字节越界。WRITE 的数据复制会覆盖这部分重叠，不能据此
认为编码边界正确。

调用实际生产编码函数，提供 capacity=40，并在其后放置两个哨兵字节：
  header rc=0 capacity=40 encoded=40 guard=0000 (expected a5a5)

说明函数返回成功、报告写出 40 字节，却改写了声明容量之外的字节。

修复建议：统一真实字段布局、保留字段宽度、头长和数据起点，确认解码也与之
一致。不需要新增 V1/V2 命名或旧格式兼容层。补一个精确容量的编码反例即可。

2. [P1] 结果淘汰会把已完成的写重新执行，覆盖后续新数据

位置：
  node_runtime/block_service.c:80  make_room_locked
  node_runtime/block_service.c:111 take_entry_locked 的满表淘汰
  node_runtime/block_service.c:328 到期删除后继续作为新操作执行

满表或结果字节预算不足时，会直接删除已完成项，不要求它已过承诺保留期。
之后重试同一操作，find_locked 找不到该键，就重新占位并执行。

复用实际 service 和文件后端的小复现：
  - 第一笔写把同一扇区写成 a5。
  - 后续 256 笔不同 operation_id 的写把该扇区更新成 5a。
  - 在默认 30 秒保留期内，重试第一笔写。

结果：
  within 30s retention: unique_writes=257 executions=257 latest_byte=5a
  retry first write: executions=258 latest_byte=a5 (expected executions=257 byte=5a)

这不是单纯缓存命中率下降，而是旧请求重新产生副作用，覆盖了更新的数据。
正常到期分支同样把 entry 清空后按新操作执行，也不符合纲领要求的过期结果
语义。

修复建议：
  - 承诺保留窗口内不能因容量压力丢掉去重证明；没有容量时，在执行新操作前
    返回可重试背压，不能先执行再放弃保留承诺。
  - 生产保留窗口须与 admitted 生命周期/路由重试窗口一致，不能只依赖默认
    30 秒就宣称合同完成。
  - 窗口过后，旧操作应返回明确的过期/typed I/O 失败，不能重新当作新写或
    新 FLUSH。需要有界且可判别的过期规则，不要求无限保留全部结果。
  - 并发重复请求等待期间的淘汰也须遵守同一规则；重新查键不等于已经保证
    不会再次执行。

3. 队列顺序语义尚未实现，单把执行锁不能替代

位置：
  common_include/wavevm_block_wire.h:43 请求结构
  node_runtime/block_service.c 的 execute_lock 执行区

新请求没有 queue_id/queue_sequence，通用 envelope 也不携带它们。
同一 service 的 I/O 虽被 execute_lock 串行执行，但它不能知道 UDP 乱序前
QEMU 要求的原始顺序。后到的 WRITE 或 FLUSH 先获得锁，仍可能违反顺序合同。

修复建议：补充并保留请求的顺序域/序号，让 WRITE、FLUSH 依照该顺序域执行。
独立队列/设备不应长期因整条 service 的一把锁全部串行化；复用既有队列和
批处理机制即可，不需要为此再设计完整的新存储调度系统。

三、对 DSH 三张交付说明截图的回应

1. 新增模块和边界说明基本诚实

目标侧 service 的确已经有真实实现和直接测试，但当前只能算存储生产链的
一个部件，尚不能宣称 QEMU -> 远端存储 -> QEMU 已闭合。

2. 测试 PASS 属实，但 FUA 证据表述需要收紧

本轮实际运行并通过：
  bash tests/control-plane/test_block_service.sh
  bash tests/control-plane/test_ingress.sh
  bash tests/control-plane/test_envelope.sh

test_block_service.c 有处理 FUA 的 callback 分支，但构造测试请求时 flags
始终为 0，没有实际运行 FUA 请求。因此可声明 WRITE+FLUSH 已覆盖，不能据此
声明 WRITE+FUA 已验证。后续补一条真实设置 FUA 并核对后端持久化调用的针对性
验证即可，不需要扩张大量测试。

这些脚本通过也没有覆盖前述精确容量编码及缓存压力后的旧写重试反例。

3. 下一步接线顺序合理

建议顺序：
  修正上述错误与顺序语义
  -> 从 admitted manifest 导出存储放置投影或等价的已准入映射
  -> main.c 初始化并注册 block service
  -> 发起端 main_wrapper/QEMU IPC 转为规范 envelope
  -> BLOCK_ACK 的接收分流、原始操作关联及完成返回
  -> 用这条真实链验证 flat/fractal 的存储合同

存储映射不能硬编码目标，也不能退回旧 hash ring。设备/卷标识及 placement
校验须一并接通；当前新请求没有设备标识，不能默认整台 VM 只有一块盘。
只需把存储职责接入统一 node runtime，本地 executor 保持本地执行职责，
无需顺带重写全部 master/slave 代码，也无需保留旧存储通信路径。

生产路径仍应是：
  QEMU -> 本地 node runtime -> 规范 envelope/路由
       -> 目标 node runtime -> 本地 storage executor -> 关联的完成结果返回

补齐上述生产实现是在关闭 R02；实现接通后做 flat/fractal 合同实测，才是
goal 第 6 项中存储子项的验证进度。最终 guest 登录/SSH 仍留在第 7 项。
