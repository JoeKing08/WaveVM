三、对报告四个问题的回答

问题 1：Operation cache 的优先级和归属

可以独立开发和做契约测试，不必等真实双节点。但在远程存储明确拒绝准入时，
它不必成为 CPU/内存 CREATE 闭环的前置条件。

cache 应位于目标 node runtime 内，靠近存储执行模块、在实际产生副作用之前，
按 VM 身份和生命周期管理。executor 是 runtime 内部模块，不是另起独立 slave
权威；gateway 也不应承担存储副作用去重权威。

必须实现的语义：
- 相同完整操作身份、相同语义：处理中合并等待，完成后重放结果。
- 相同身份、不同语义：拒绝冲突。
- 缓存结果过期：明确返回过期，不因“查不到结果”就重新执行写入。
- digest 覆盖操作、设备、地址、长度、标志及数据，不能只有 SHA256(data)。
- 保持不同队列并行，不能用全局串行化代替队列顺序。
- Flush/FUA 要从设备请求一路传到真实执行边界，并有对应持久化完成依据。

“拒绝所有重复 operation_id”不是正确的重试协议；completion 丢失后的相同请求
需要能安全获得此前结果。缓存有界性和保留期也必须与重试窗口契约一致。

问题 2：CI 是否可以绕过控制面

不要新增绕过控制面的生产启动路径。
测试夹具可以继续用于组件烟测，但不能把这种测试称为正式 CREATE 验收。
CI 最终应调用真正的控制面和统一 node runtime，不需要恢复旧 CLI 或旧独立进程。

CI 改写可与生产接口接线并行准备，但不能通过制造固定 evidence、固定 ACK 或
预先拼好成功状态来代替真实准入。组件测试与生产闭环测试应明确区分。

问题 3：最小 CREATE 的可验收范围

最小闭环有意义，建议先用 Mode B，而不是以 Mode A 内核问题作为依赖。
Mode A/B 与 KVM/TCG 是独立维度，此建议不意味着 Mode B 只能使用 TCG。

先用单机回环上的真实控制端和参与端、本地 QEMU 磁盘，完成：
  注册 -> 实际能力探测 -> JOIN/路由确认 -> ACTIVE
       -> CREATE prepare/activate/commit -> 销毁及资源释放

JOIN 应在成员可调度之前完成，不是 CREATE 后再补。
ACK、能力证据、资源预留必须真实，不能用固定成功值替代。
同时验证失败回滚、重复请求、参与者不可达及资源释放。

优先连接现有 ctl_tool、coordinator、admission、cluster 与 runtime 接口。
已有 placement 算法和状态机，不是需要从零重写所有规划逻辑；主要缺口是
生产输入、真实传输和调用闭环。应先逐项识别可复用实现，避免无谓扩大任务。

单机闭环只能证明这一阶段的生产组合路径；不能用它宣称分布式和 guest 启动
已经通过。后续再进行双节点控制/数据通路烟测，最后是完整 guest/SSH 验收。

问题 4：推荐顺序、验收及风险

推荐顺序：回归修复 -> C -> A -> B。

第一步：修 F14，收紧未完成远程存储能力的准入，并撤掉不成立的“已完成”结论。
Mode A 的 context 问题应明确保留为未完成项，不能靠 per-CPU 改名算作解决。

C：打通正式 CREATE，同时验证失败回滚、重复请求和资源释放。
在最小范围内接通真实接口，不需要先把完整 guest 启动作为控制面验收条件。

A：完整接通 typed 存储，再验证重复写只执行一次、completion 丢失后的重放、
不同语义冲突、结果过期、队列顺序与 Flush/FUA 持久化。
只加 cache 而继续通过旧网络包执行，无法补齐这些语义。

B：迁移双节点 CI，先验证控制和数据通路，再做完整 guest/SSH 验收。
CI 脚本准备无需机械地等待 A，但远程存储未通过时必须显式排除该能力，
不能让不完整的实现参与准入后又把结果视为整个系统通过。

风险边界：
只要各阶段复用正式接口、明确未支持能力并拒绝相应准入，就是分阶段实现，
不是 workaround。新增 CI 专用生产旁路、包裹旧协议冒充 typed 契约、
或用全局串行化掩盖生命周期与排序问题，才会继续累积架构债。

保留 MPSC、多队列和异步 diff 等优化方向；修正其所有权、排序及生命周期边界，
不要为了先获得 PASS 就将其永久删除或变相全局串行化。
