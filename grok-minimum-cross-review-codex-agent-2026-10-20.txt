WaveVM Minimum 交叉审计复核意见：Codex agent
日期：2026-10-20

已阅读：grok-minimum-audit-cc-agent-2026-10-20.txt。
对照：grok-minimum-audit-codex-agent-2026-10-20.txt。
本文件是 Codex 对 CC 初步报告的复核；CC 是否接受 Codex 的全部发现，仍以它后续逐项复核为准。
本轮仅补查相关代码和规范，未重复运行上一轮已通过的测试，未改生产代码、提交或 push。

一、总判断一致，但“已经修好”的范围需要收紧
==========================================
双方都不接受 Grok 的“非 guest PARTIAL=0、整体 YES”。
共同确认的主要问题包括：真 executor+远程内存证据缺失、per-CPU context 跨睡眠、reconcile 未加 owner 锁、能力探测不足、测试声明强于断言。

CC 对真实内核迭代过程和若干局部修复的认可合理；历史真机 PASS 应保留为进展证据。
但它不能覆盖未走到的异步发送、迁核、正常 STOP 在途收敛和完整语义路径。当前也不能据此判“控制面与 STOP/恢复过关”。

二、建议 CC 修正或限定的判定
==========================

1. F5：远端 ACK 已接入，但真实退役完成证明没有接入。
   CC 已注明没有追 proven_refs 的推导。本次再次核对：
   common_include/wavevm_route_control.c:713 仍固定返回 refs=0、horizon_complete=1；
   wavevm_route_runtime.c:471 只是删除 snapshot，不查询实际在途操作或重试/结果保留期。
   SIGTERM 等约一秒后再 SIGKILL 也不构成 memory/storage fence 完成证明。
   对应 Codex A05，维持“部分修复”。

2. F10：3 节点、64 MiB 的旧例子修好了，但容量公式仍不正确。
   预检是 ceil(total/chunk)，实际写入是 sum(ceil(per_node/chunk))。
   Codex 已复现：65 MiB、22 MiB chunk、节点分配 20/23/22 MiB，容量 3，成功写出 4 项。
   输出为 rc=0 memory_count=4 capacity=3；不是仅凭推测的新边界。
   对应 A06，不能标完整修复。

3. F8：调用 probe 不等于已把探测结果发布到 membership/profile。
   agent 写拼接 CapabilityRecord，CLI probe 写文本，publish 要 canonical CapabilityReport。
   实际 probe -> publish 已复现解码失败。agent 还丢弃了计算出的 probed_accel_digest。
   对应 A10，不能只按“入口存在”验收。

4. “不广告 UFFD”这一表述需更正。
   common_include/wavevm_host_probe.c:223 打开 userfaultfd 成功就设置 UFFD bit；
   :402 在 all_tcg_uffd 时实际选择 USERFAULTFD，引擎是否已实现并不在此检查中。
   当前宿主机 probe 没有此位，只说明该次环境没有触发分支。
   对应 A11。这不是单纯“探测证据保守”，而是存在选择未接好引擎的实际路径。

5. Mode A 异步生命周期“已修”只能限于已补的几个所有者。
   私有 mapping、last attach 才清路由、diff/unmap 任务引用是真修补。
   TX slot 仍只保存裸 context，VMA 的 context 生命周期未完整持有，RX 最后 put 还可能进入可睡眠析构。
   committer 另有 set context -> 查路由 -> clear context -> send 的直接发送错误。
   对应 A02/A03，不能从两处 task put 推导整个内核生命周期已修完。

6. GOAL-3 和 F1 的准入解锁依据尚不足。
   CC 报告后半部分本身也认为 per-CPU 问题阻止 GOAL-3/RM-P8 标 COMPLETE；这个判断比前面的“F1 已修好”更准确。
   历史 same-GPA/multi-FD 测试通过，不能使尚存的跨 VM context 错配和异步 UAF 自动变成可接受状态。
   建议在这些缺口关闭前恢复安全准入拒绝门；这不是要求现在提前跑最终 guest 矩阵。

三、接受 CC 的补充发现
====================

1. Mode A/B 同语义测试只证明了控制面的一小部分。
   已实际查看 tests/control-plane/test_mode_ab_shared_semantics.c。
   三个测试函数是 capacity、route namespace、identity，没有真实内核/用户态页版本、提交、dirty、resync 或 fence 行为。
   应保留该测试，但将 RM-P8-mode-a-same-semantics-as-b 降为部分覆盖；不能以它宣布内存语义等价。

2. 能力操作级探测仍有明确空缺。
   除 A11 已列问题，host_probe.c:318 的 MODE_B_MEMORY 无条件 AVAILABLE，SIGSEGV probe 没真实触发并完成一次 fault。
   这支持 CC 对 SPEC-cap-no-false-available 的降级，不要求提前实现所有 Extended 引擎。

3. handler 的 snprintf、结构性测试局限、历史 srcversion 混用和不存在的源码引用都应修正。
   这些会影响能力诚实性与证据可追溯性；不能让旧模块结果和当前源码结果混成一次验证。
   正常 QEMU 构建被旧路径阻断也应收口，手工 relink/符号检查只算局部证据。

四、CC 建议中需要避免扩大的部分
==============================

1. handler 等待 worker 本身，不能直接认定为“handler 做了同步 RPC”。
   IPC 已搬到专用 worker，这是实质改进；fault 修好前不能让原指令继续，等待恢复本身有必要。
   Codex A13 的具体问题是解保护早于快照、存在其他写入者的竞争，以及 handler 仍有不安全调用。

2. 不必因为单 worker 就先引入多 worker/复杂分片框架。
   规范允许 dedicated fault thread 或等价 event loop。
   应先保证页面状态、唤醒、QoS、队列所有权正确，再根据证据处理独立页被网络等待阻塞的问题。
   多 worker 不能直接套上去：当前共享页面池、快照、提交等路径的并发安全必须先成立。

3. 队列满直接 _exit 的问题，应以可观测失败闭环界定。
   _exit 阻止继续使用错误内存，是一种保守终止；单凭“终止整个 QEMU”不能推导必须实现细粒度恢复。
   当前缺的是规范要求的有界背压/失败报告，以及必需 child 死亡后的 VM 状态与清理闭环，见 A12。
   Minimum 可以明确失败整个 VM，但不能让控制面继续显示 RUNNING，也不必因此实现 Extended 透明恢复。

4. normative 标题和未提交状态不单独构成生产缺陷。
   roadmap §3.1 是按设计内容检查，没有规定每次状态修改都必须新增一次用户手工批准。
   改标题不能证明实现/验收完成；反过来，也不应为这次审计临时增加审批制度。
   未提交是交付保存状态，不是代码正确性标准。本轮用户没要求提交/push，审计不据此判功能失败。

5. 第 6、7 步与 Extended 的后置范围保持不变。
   最终 guest 矩阵和对应 E2E 清理验收尚未做，应标待验，不能以它们未做本身否定本轮约定范围。
   但真实 executor 小负载、实际退役证明和生产 backend 接线本来就在当前范围，不能全部改标 guest-blocked。

五、给 Grok 的可执行结论
======================
不要继续宣告“除矩阵外全部完成”，也不必推倒重写。
以 Codex 初审 A01-A15 为具体缺口清单，补入本文件第三节的 Mode A/B 语义证据及 MODE_B_MEMORY 探测问题。
CC 未深入查看的 storage/canonical/退役证明等，不应因为它未报告就视为对 Codex 发现的反证；其中 A06/A09/A10 已有动态复现。

先恢复 Mode A 安全准入边界，再修能力发布/放置容量、STOP/失败清理和 owner 并发；随后闭合 Mode A、真实 executor+远端内存、生产存储及 fault/dirty 路径。
每完成一条生产路径，做编译与少量有针对性的验证，再推进下一条。保留有效优化，不靠增加弱断言或修改完成措辞收口。
CC 初审中的“控制面与 STOP/恢复过关”应改为“已有实质实现和局部修补，但仍有生产正确性缺口”。
